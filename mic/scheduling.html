02

FREERTOS / FIXED-PRIORITY PREEMPTION

The most urgent ready task wins.

A task’s priority stays fixed unless the application or an inheritance mechanism changes it. The scheduler selects the highest-priority task that can actually run.

Interrupt or tick→Update ready lists→Highest priority→Run

Ready is the key word.

A high-priority task waiting for a notification, delay, or mutex is blocked. Lower-priority work can run while it waits. When the event arrives, preemption lets the high-priority task take over.

With configUSE_PREEMPTION = 1 and configUSE_TIME_SLICING = 1, ready tasks at the same highest priority rotate at tick boundaries.

TRY THIS / ABOUT 2 MIN

Can a tick make B outrank C?

Step to t = 3: C becomes ready at priority 4 while A and B have priority 2. Turn time slicing off, then try cooperative mode.

Trace the decision in pseudocode
on scheduling event:
  update task states
  if preemption enabled or current task blocks/yields:
    p = highest priority with a ready task
    next = ready_list[p].selected_task
  on tick, if preemption and time slicing enabled:
    rotate among ready peers at priority p

Disabling time slicing does not disable higher-priority preemption. Cooperative scheduling is a separate configuration. An explicit yield also provides a scheduling opportunity.

03

LINUX EEVDF / FAIR-CLASS SCHEDULING

Fairness first. Then the earliest deadline.

EEVDF asks two questions: “Is this task owed CPU time?” and “Among those tasks, whose virtual deadline is earliest?”

ACCOUNT FOR SERVICEvᵢ += Δt / wᵢ

More weight means virtual runtime grows more slowly.

FILTER BY ELIGIBILITYlagᵢ = wᵢ(V − vᵢ) ≥ 0

A nonnegative lag means the task is owed service.

ORDER ELIGIBLE TASKSdᵢ = vᵢ + sliceᵢ / wᵢ

At request creation, assign a virtual deadline.

A virtual deadline is not a wall-clock promise.

It orders service requests inside the fair scheduling class. EEVDF does not provide the reservation and admission-control semantics of Linux SCHED_DEADLINE.

In this model, V is the weighted mean of runnable virtual runtimes. All three tasks stay runnable. A consumed request receives a new virtual deadline; it is not recomputed after every unit of partial service.

TRY THIS / ABOUT 3 MIN

More CPU, or sooner CPU?

Set B’s weight to 4 and watch its service share grow. Then keep its weight fixed and change its request size. Inspect the eligibility and deadline columns at each step.

Why can an earlier deadline lose?

Eligibility comes first. A task with negative lag is ahead of its fair share, so this model excludes it even if its deadline is the smallest. As other tasks execute, V advances and that task becomes eligible again.

Linux adds mechanisms for sleeping tasks, lag placement, request protection, and efficient runqueue selection. This deliberately small model re-evaluates at integer boundaries and omits those implementation details.

04

LINUX PREEMPT_RT / PREEMPTIBLE KERNEL EXECUTION

The right priority needs a path to run.

PREEMPT_RT is a kernel configuration, not a competing fair scheduler. It reduces scheduling latency through preemptible locking and threaded interrupt handling, alongside policies such as SCHED_FIFO.

Follow a priority inversion.

A low-priority task A owns a mutex. High-priority C needs it and blocks. Medium-priority B is ready. Without inheritance, B delays A, which delays C—even though C outranks B.

With priority inheritance, A temporarily inherits C’s priority, completes its critical section, and releases the mutex. C can then run. Inheritance bounds interference from B; it does not remove the critical section.

TRY THIS / ABOUT 2 MIN

Let the lock owner finish.

Compare inheritance on and off. Inspect t = 2, when B arrives. Watch A’s effective priority and note the first interval in which C runs.

ANOTHER PIECE OF PREEMPT_RT: INTERRUPT THREADING

Device IRQ→Short hard-IRQ handler→Wake IRQ thread→Scheduled handler

Most interrupt work becomes schedulable thread work. Low-level entry paths, raw spinlocks, and some interrupt handlers remain non-preemptible.

What this experiment does—and does not—compare

Both traces use idealized fixed-priority SCHED_FIFO tasks with instantaneous dispatch. The switch controls whether this mutex donates priority. It is not an RT-versus-stock Linux benchmark: priority inheritance is also available for explicitly configured user-space mutexes without PREEMPT_RT.

We omit RT bandwidth throttling, CPU affinity, migration, interrupt load, and context-switch overhead. PREEMPT_RT alone does not guarantee every application deadline.

06 / CHECK YOUR INTUITION

Predict. Run. Explain.

01 / Does round robin give low-priority tasks a turn?

Not when a higher-priority task is continuously ready. FreeRTOS time slicing rotates peers at the highest ready priority. Block the high-priority task to let lower-priority tasks run.

02 / Does the smallest EEVDF deadline always win?

No. First check eligibility. Only a task with nonnegative lag competes for the earliest virtual deadline in this model.

03 / Does priority inheritance make C run immediately?

No. C still needs the mutex. Inheritance lets A finish the blocking critical section without interference from medium-priority B.

04 / Does PREEMPT_RT replace EEVDF?

No. It changes kernel preemptibility and synchronization. Fair-class tasks still use the fair scheduler; real-time policies select RT tasks.
