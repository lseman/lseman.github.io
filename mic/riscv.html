01 / START WITH AN EXAMPLE

Four ideas run this pipeline.

Each example below loads a program into the simulator. Use Step to follow the same instruction from IF through WB.

01ONE STAGE PER CYCLE

Pipelining

Each instruction passes through fetch, decode, execute, memory and write back. A new one enters every cycle, so up to five are in flight and the ideal is one instruction per cycle (IPC = 1). Every stall or flush pulls IPC below that.

Instruction and data memories are separate; lw/sw access aligned 32-bit words at rs1 + imm, and x0 is always 0.

Observe: the first instruction takes five stages to complete. Subsequent instructions overlap: five instructions without stalls finish in nine cycles. The benefit is higher throughput.

02KEEP THE DATA MOVING

Data hazards

An instruction often needs a result that has not been written back yet. Forwarding from EX/MEM and MEM/WB delivers it in time for ALU results. A load's data only exists after MEM, so a dependent instruction right behind it still waits one bubble.

Observe: lw x1, 0(x0) reads 7 from the initial memory. The following add x2, x1, x1 needs that value and waits one cycle; it then receives 7 through forwarding and produces 14. The producer advances while the consumer waits.

03CHOOSE THE NEXT PATH

Control hazards

Branches and jumps resolve in EX, two cycles after fetch. Fetch predicts the next PC; a wrong prediction squashes the two younger instructions in IF and ID, and the corrected PC is fetched next cycle. There are no delay slots.

Observe: bne returns to the decrement while x1 is nonzero. A correct prediction keeps instructions flowing; an incorrect prediction discards the wrong path and redirects the PC. Compare modes in the prediction tab.

04WAIT FOR A BUSY UNIT

Structural hazards

With RV32M enabled, a multiply holds EX for 3 cycles and a divide for 16. Nothing can pass it: the hazard unit holds PC, IF/ID and ID/EX, and EX/MEM receives a bubble each cycle until the result is ready.

Observe: in this core, multiplication and division occupy EX until the result is ready. This blocks subsequent instructions, even independent ones. The designs in Execution units illustrate other ways to overlap operations.

How to follow an execution
  1. Load: choose an example above, or edit the assembly and click Load program. Editing the text alone does not change the running program.

  3. Follow: the five cards show work during the last completed cycle. Compare them with registers, memory, and signals; the pipeline registers hold values for the next cycle.
  4. Go back: use Back and the timeline to compare cycles. After rewinding, Step replays saved cycles before advancing execution.

How to interpret the counters

IPC: instructions completed per cycle over the last 64 cycles, or all available cycles if fewer. CPI: the reciprocal of this IPC; shown as “—” when no instruction has completed within the window. Low IPC is expected while the pipeline fills.

Bubbles: bubbles counted while waiting for load-use data or the multiply/divide unit. Mispredictions: recoveries from incorrect predictions; one recovery can discard more than one instruction.

For an ideal program with N instructions and five stages, starting empty and running until the pipeline drains: cycles = N + 4. The whole-program CPI matches the counter only when the entire execution fits within its window. To compare elapsed time, use cycles × clock period.

Registers as x0–x31 or ABI names (a0, sp, ra…). Branches and JAL accept labels (loop: addi a0, a0, -1 / bne a0, zero, loop) or byte offsets relative to the instruction. Labels are case-sensitive. LUI/AUIPC take an unshifted 20-bit immediate.

Stall, bubble, forwarding, or flush?

Stall: holds an instruction in place because it cannot advance yet. Bubble: a stage spends a cycle without a useful instruction. During a load-use stall, IF/ID is held and a bubble enters EX; older instructions continue.

Forwarding: sends a result from EX/MEM or MEM/WB directly to its consumer in EX, without waiting for register writeback. The dependency remains, but the value arrives in time.

Flush: invalidates younger instructions fetched along the wrong path. They must not change architectural state. An empty card can also indicate normal pipeline filling or draining: check the events before attributing it to a hazard.

Prediction & control signals

Inspect predictor tables and pipeline valid bits

BTB index = PC[5:2], with a full PC tag. Bimodal counter index = PC[5:2]; gshare index = PC[5:2] XOR resolved history. Counter states: 0 strong not-taken, 1 weak not-taken, 2 weak taken, 3 strong taken. A BTB miss always falls through, even if a shared counter predicts taken.

IndexDirection counterBTB PC tagTargetKind

Prediction uses the table state at the start of the cycle; EX trains it later. Gshare shifts only resolved conditional outcomes, so it needs no speculative-history rollback. Wrong-path IF/ID work never trains the tables. Indirect jumps use the last resolved target; returns have no dedicated stack in this model.

    How this datapath works · model boundary
    Control travels with the instruction

    Each latch carries a valid bit and the fields needed downstream. ID/EX carries operands, source/destination indices, PC, PC + 4, immediate, prediction metadata and EX/MEM/WB controls. EX/MEM carries the execution result, store data, rd and MEM/WB controls. MEM/WB carries load/result data, rd and WB controls. Dashed bundles represent these fields; local control fan-out is abstracted.

    Forwarding before operand selection

    For each used source, choose EX/MEM first, then MEM/WB, then ID/EX. Require RegWrite and rd ≠ x0; never forward a load address. Forwarded rs2 feeds the branch comparator and store-data latch independently of the ALU immediate input. WB writes before ID reads in the same cycle.

    Hold, bubble, or redirect

    The hazard unit compares a load’s ID/EX.rd with the used IF/ID source indices. On a match, hold PC and IF/ID and clear ID/EX for one cycle. EX compares predicted and actual next PCs: a mismatch clears both younger instructions and fetches the corrected PC next cycle. Correct predictions keep the pipeline moving. The control plane shows source indices, load qualification, producer metadata, mux selects, and recovery priority.

    Fetch predicts; EX verifies

    A tagged BTB supplies known branch and jump targets. Two-bit counters supply branch direction; gshare mixes the PC with four bits of resolved history. The instruction carries its predicted next PC and table index into EX. Only a next-PC mismatch redirects; an untaken branch can therefore recover to PC + 4. Predictor training cannot override an older memory fault.

    Model boundary: conceptual datapath, not a gate-level netlist. Separate single-cycle memories; no caches, compressed instructions, CSRs, interrupts or privilege modes. This lab stops and drains older work on an invalid data access or misaligned target instead of entering a trap handler. Running beyond the loaded program drains the pipeline. RV32I instruction reference ↗

    Where modern high-performance cores go next

    This is a single-issue, in-order core with a small educational predictor. Larger designs add history-based predictors such as TAGE, a return-address stack, instruction caches and fetch queues. Out-of-order execution also needs register renaming, issue queues, a reorder buffer, load/store ordering, and precise recovery. Those mechanisms are beyond this simulator.       06 / DESIGN THE EXECUTION UNIT

      One instruction. A whole machine inside.

      Multiplication and division can live in independent hardware modules. Explore the work inside each unit, then see how latency and throughput change its schedule.

      The workbench's RV32M unit treats these designs as fixed latencies: multiply holds EX for 3 cycles, like the 3-stage pipeline here, and divide for 16, like an iterative radix-4 divider on 32-bit operands. This lab opens those cycles up with unsigned 8-bit operands, so every algorithm step stays visible. RISC-V’s M extension defines results, not cycle counts.

      Latency = cycles from acceptance to result. Initiation interval (II) = minimum cycles between accepted inputs. A shorter II helps independent work; a dependency chain waits for each result.

      Four requests through one module

      Why four? One request shows latency; several show the initiation interval: how soon the next request may start. Inputs are accepted at cycle boundaries. Blue cells show work during that cycle; green marks the result boundary. This schedule assumes no output backpressure.

      All steps of request 1 as a table

      Multiply: split the long path

      A multiplier generates shifted partial products, reduces them with carry-save adders, then uses a carry-propagate adder. Registers between these blocks shorten the combinational path. A balanced reduction tree and Booth recoding can reduce depth or partial-product count; the 3-stage example uses ordinary partial products.

      More stages can raise clock frequency and throughput, but add latency, registers, clock power, and forwarding complexity. Compare elapsed time as cycles × clock period, not cycles alone.

      Divide: reuse or replicate

      A radix-2 divider produces one quotient bit per iteration, reusing a compare/subtract datapath. Radix-4 produces two bits, selecting from 0×, 1×, 2×, and 3× the divisor. The example fully unrolls four radix-4 steps with a register after each, so different requests overlap.

      An iterative radix-4 unit could reuse one stage for four cycles instead: less hardware, II = 4. Early-out or leading-zero detection can reduce work for some operands, but makes latency variable. Our examples keep fixed latency, including division by zero.

      Connect modules to the core

      Use req_valid / req_ready to accept operands and resp_valid / resp_ready to return a result plus its destination tag. Hold payloads stable under backpressure. A scoreboard tracks pending registers; consumers wait or receive a forwarded result.

      Separate ALU, multiplier, divider, and load/store units can overlap with appropriate issue logic. This needs writeback arbitration and, for precise state, ordered retirement. Branch flushes must cancel or discard tagged younger work. Adding a module alone does not give the five-stage core this scheduling behavior.

      RV32M results and corner cases

      MUL returns the low 32 product bits; MULH / MULHU / MULHSU return the high half with signed/signed, unsigned/unsigned, or signed/unsigned inputs. DIV / DIVU return a quotient; REM / REMU return the remainder. Signed division truncates toward zero, and a nonzero remainder has the dividend’s sign.

      For RV32 division by zero, the quotient is 0xffffffff and the remainder is the dividend. Signed −2147483648 / −1 returns −2147483648 with remainder zero. These cases do not trap. Hardware can share work for matching quotient/remainder pairs or high/low product pairs.

      The trace below the controls is an 8-bit teaching model: its divide-by-zero quotient is 255 and remainder is A. Read the official M-extension specification ↗

        From simulation to an FPGA
        The memories here read combinationally to keep the timing identical to the simulator. FPGA block RAM reads on a clock edge, so a real softcore registers the fetch address one stage earlier, or adds a pipeline stage. Replace the testbench with a top level that drives a clock, a reset button and a few LEDs from a memory-mapped address, and the same core runs on hardware.
